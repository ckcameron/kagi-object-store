# S3 compatibility (experimental)

The optional `s3` node configuration starts a separate path-style listener. The
native REST API remains on `listen`. The S3 listener always configures request
signature authentication through `s3s`; anonymous requests cannot reach storage.
Use AWS Signature V4 credentials with a custom endpoint and path-style addressing.
TLS uses the node certificate. Without TLS the listener must bind a loopback IP.

```yaml
s3:
  listen: "127.0.0.1:7480"
  max_object_bytes: 67108864
  credentials:
    MY_ACCESS_KEY:
      secret_key: "REPLACE_WITH_AT_LEAST_32_RANDOM_SECRET_BYTES"
      uid: 1000
      gids: [1000]
      buckets: [example-bucket]
      read_only: false
```

`credentials` is an explicit access-key map, not an IAM implementation. Each entry
requires exactly one of `uid` or `directory_user`. A `directory_user` is resolved
through native NSS on each authenticated request; a failed lookup denies access.
Its resolved UID, supplementary groups and available AD user/group SIDs feed the
existing filesystem ACL evaluator. Client-supplied Kagi identity headers are
ignored. Fixed `uid` identities use `gids` (default empty). `buckets` is a required,
nonempty allowlist; `read_only` defaults to false. Credentials are local node
configuration: keep them protected and consistent on all serving nodes. Restart
nodes to change configuration. See [directory resolution](DIRECTORY-IDENTITY.md).

Implemented operations:

- Create, head, list and delete buckets, with nonempty-bucket checks.
- Put, get, head and delete objects; GET byte ranges, ETags, content type and user
  metadata; GET ETag preconditions and PUT conditional creation/replacement.
- ListObjects and ListObjectsV2 with prefix/delimiter grouping, bounded page sizes
  and continuation markers.
- Initiate, upload part, list parts, complete, list and abort multipart uploads.
  Completion checks increasing part numbers, exact part ETags and the 5 MiB
  minimum for every nonfinal part. The complete ETag uses the multipart digest.
  Multipart listing supports prefix and key/upload-ID markers, not delimiter.

`s3s` parses signatures, XML, query parameters and streaming signed bodies.
Kagi verifies Content-MD5 and supplied checksum headers/trailers before publishing
uploaded data. SHA256 payload authentication is provided by the signed-body
adapter. Unknown operations return S3 errors. Unsupported security options must
not be interpreted as successfully applied policies.

Multipart records and part manifests are replicated in Raft. Parts themselves
use the existing encrypted distributed fragment storage, never plaintext staging
files. Completion publishes the object, updates an existing filesystem parent,
and removes the upload in one Raft state-machine operation. Replaced/aborted/
completed parts enter fenced garbage collection after the configured grace.
Incomplete uploads remain until explicitly aborted. Failed writes before a
metadata commit can leave orphan fragments, as in the native object path.

Reads use a quorum barrier and writes wait for Raft commit. Send requests to the
current leader; follower or quorum-unavailable requests return ServiceUnavailable.
Bucket allowlists, object policy, ACLs and default bucket retention remain in force.
S3 deletion installs an internal Kagi delete marker; historical Kagi versions are
retained and remain accessible through the native version API. This is not S3
versioning. S3 deletion of a currently retained/held object is denied.

Limits and exclusions:

- Objects, individual parts and assembled uploads are buffered, bounded by
  `max_object_bytes` (default 64 MiB). The listener admits at most eight concurrent
  requests. This is not a streaming multi-terabyte object implementation.
- No IAM, STS, bucket policy, public ACL, S3 versioning, CopyObject, multi-delete,
  lifecycle, S3 Object Lock administration, KMS/SSE-C, virtual-host routing or
  encoding-type listing support. Native Kagi retention/encryption still apply.
- Date-based conditional reads, conditional HEAD and some optional response or
  storage headers are not part of the supported subset. Use the documented core
  operations; broader SDK conformance remains a release gate.
- Multipart completion responses are not retained for indefinite retry after
  completion; a subsequent call may report NoSuchUpload. Incomplete-upload expiry
  is not automatic.

The integration test `s3::tests::signed_http_storage_multipart_restart_and_denials`
uses curl's independent AWS signing implementation against a real local listener,
including escaped keys and metadata reload. It does not establish full AWS SDK or
AWS S3 conformance. All nodes must support the new Raft commands before enabling
S3. Mixed-version rollback after S3 writes requires an explicit migration plan.
